# 07. 四人打ち麻雀（1局勝負）仕様書

## 1. 概要とゴール

CPU 3 人と対戦する四人打ちリーチ麻雀。**東 1 局のみの単発勝負**で、1 プレイ 3〜7 分。既存ミニゲームが「部分技術の練習」だったのに対し、本ゲームは打牌・鳴き・立直・ベタオリの総合実戦の場を提供する。

### スコープ

- 東 1 局のみ（和了または流局で終了。連荘・南入なし）
- **鳴きフル対応**: ポン・チー・カン（暗槓/明槓/加槓）、搶槓・嶺上開花・槓ドラ
- CPU 3 人は標準 AI（牌効率で手を進め、立直者にはベタオリする守備あり）
- プレイヤーが操作するのは自家のみ
- [04-architecture.md](04-architecture.md) の規約に準拠: `src/games/four-player-mahjong/` + `gameRegistry.ts` 1 エントリ追加

### 非スコープ（第 1 版では作らない）

- 東風戦・半荘戦などの複数局進行（積み棒・連荘・順位戦・トビ終了）
- ダブロン・トリプルロン（頭ハネで単一和了に裁定）
- 途中流局（九種九牌・四風連打・四家立直・四槓散了）
- CPU 難易度選択（AI は「標準」1 種のみ。将来は判断関数の差し替えで拡張）
- パオ（責任払い）・流し満貫・ダブル役満

## 2. ルール仕様（確定事項）

「1 局のみ × 鳴きあり」で裁定が必要な全項目。実装はこの表を正とする。

### 基本

| 項目 | 裁定 | 備考 |
|---|---|---|
| 局 | 東 1 局のみ。和了または荒牌流局で終了 | 連荘・積み棒・南入なし |
| 起家（親） | 4 人からランダム（シード付き RNG で決定） | プレイヤー固定親は不採用（点数体験が偏るため） |
| 持ち点 | 25000 点持ち。終了時に増減と最終持ち点を表示 | トビ判定なし。箱下は負数のまま表示 |
| 赤ドラ | 各色 1 枚（計 3 枚）、各 1 翻 | `createShuffledWall` の既定と一致 |
| 喰いタン・後付け | ともに**あり**（ありありルール） | |
| ノーテン罰符 | あり。場 3000 点（1 人テンパイ +3000 / 2 人 ±1500 / 3 人 +1000）。形式テンパイを認める | 1 局のみでもテンパイ維持に意味を持たせる |

### 立直

| 項目 | 裁定 | 備考 |
|---|---|---|
| 宣言条件 | 門前・テンパイ・持ち点 1000 以上・残りツモ 1 回以上 | |
| 供託 | 1000 点。和了者が取得。**流局時は宣言者に返却** | 次局がないため没収は不採用（ゼロサム維持） |
| ダブルリーチ | あり（2 翻、立直と置換）。第 1 巡で自分の打牌前に鳴きが入ると不成立 | |
| 一発 | あり。間に鳴き（暗槓含む）が入ると消滅 | |
| 裏ドラ・槓裏 | あり。立直和了時のみ開示 | |
| 立直後の自動進行 | ツモ切り自動。ツモ和了・暗槓可否の確認のみ挟む | |
| 立直後の暗槓 | ツモった牌自身で構成し、かつ待ち・面子構成が変わらない場合のみ可（送り槓禁止） | |

### カン・ドラ

| 項目 | 裁定 | 備考 |
|---|---|---|
| カンの種類 | 暗槓・明槓（大明槓）・加槓。上限は嶺上 4 枚ぶん（計 4 回） | 四槓散了は採用しないため 5 回目は発生し得ない |
| 槓ドラ | あり。**カン成立時に即めくり**（暗槓/明槓/加槓とも） | 「明槓は打牌後めくり」（天鳳式）は変種として不採用 |
| 搶槓 | **加槓に対してのみ**ロン可。暗槓への国士無双の搶槓はなし | 搶槓されたら加槓は不成立（槓ドラもめくらない） |
| 嶺上開花 | あり（1 翻）。ツモ符 2 符も加算する。支払いは通常ツモ（明槓の包なし） | |
| 海底でのカン | 不可（嶺上ツモができないため） | |

### 和了・フリテン

| 項目 | 裁定 | 備考 |
|---|---|---|
| ダブロン | **頭ハネ**（放銃者から反時計回り＝ツモ順で最も近い 1 人のみ和了） | |
| フリテン | 3 種: ①自河に待ち牌がある ②同巡内見逃し（次の自分のツモ番まで） ③立直後見逃し（永続） | フリテン中はロン不可・ツモ和了は可 |
| 海底摸月・河底撈魚 | あり（各 1 翻） | 河底の打牌には鳴きも不可 |
| 天和・地和 | あり（役満）。人和はなし | 地和は子の第 1 ツモ和了（それまでに鳴きがないこと） |
| 役満 | 複合あり（`HandValue.yakuman` の倍数をそのまま使用）。数え役満・四槓子あり | `calcScore` が対応済み |
| 喰い替え | **現物喰い替えのみ禁止**（スジ喰い替えは許容） | |

## 3. データモデル

座席は絶対インデックス（`0` = 自家 = 画面下、以降反時計回り: `1` = 下家 = 右、`2` = 対面 = 上、`3` = 上家 = 左）。風は `(seat - dealer + 4) % 4` で導出する。

```ts
export type Seat = 0 | 1 | 2 | 3;

export type MeldType = "chi" | "pon" | "minkan" | "ankan" | "kakan";

export interface MeldCall {
  type: MeldType;
  tiles: TileId[];            // 実牌（赤含む）。chi/pon = 3 枚、kan = 4 枚
  calledTile: TileId | null;  // 鳴いた牌。ankan は null
  from: Seat | null;          // 鳴いた相手。ankan は null、kakan は元のポンの相手
}

export interface RiverTile {
  tile: TileId;
  riichiDeclare?: boolean;    // 立直宣言牌（横向き表示）
  called?: boolean;           // 他家に鳴かれた牌（河ではグレー表示）
}

export interface PlayerState {
  hand: TileId[];             // 門前部分（理牌済み。ツモ牌は含めず Phase 側で持つ）
  melds: MeldCall[];
  river: RiverTile[];
  score: number;
  riichi: null | { turn: number; double: boolean; ippatsu: boolean };
  furiten: { river: boolean; temporary: boolean; riichi: boolean };
}

export interface RoundState {
  wall: TileId[];             // 生牌山（先頭からツモ）
  deadWall: TileId[];         // 王牌 14 枚（嶺上 4 + 表示牌 5 + 裏 5）
  doraIndicators: TileId[];   // めくれている表ドラ表示牌
  players: [PlayerState, PlayerState, PlayerState, PlayerState];
  dealer: Seat;
  turn: Seat;
  phase: Phase;               // → 5 章
  kyotaku: number;            // 供託（立直棒）
}
```

## 4. core 拡張設計

### 互換方針（最重要）

既存の公開 API（`evaluateHand` / `scoreHand` / `shanten` / `ukeire` / `discardOptions` 等）の**シグネチャは一切変更しない**。副露対応は**新関数の追加**で行い、`yaku.ts` 内部の共通ロジック（`wholeHandYaku` / `enumerateWaits` / 符計算）は内部関数として共有リファクタする。既存テストはすべて green のまま維持する。

### 変更・新規ファイル一覧

| ファイル | 変更 | 内容 |
|---|---|---|
| `src/core/meld.ts` | 新規 | `MeldType` / `MeldCall` 型、`meldKind` / `isOpenMeld` / `meldTiles` 等のユーティリティ |
| `src/core/win.ts` | 新規 | 副露対応の役・符・点数評価 `evaluateWin`（下記） |
| `src/core/yaku.ts` | 内部リファクタのみ | 共通役判定・符計算を `win.ts` と共有。`evaluateHand` は不変 |
| `src/core/agari.ts` | 関数追加 | `decomposeConcealed(counts, meldCount)`: 門前部分を (4 − meldCount) 面子 + 1 雀頭に分解 |
| `src/core/shanten.ts` | 関数追加 | `shantenWithMelds(concealedCounts, meldCount)` / `waitKindsWithMelds(concealed, melds)`。副露ありは標準形のみ（七対・国士は meldCount = 0 限定） |
| `src/core/tile.ts` | 関数追加 | `countDora(tiles, indicators)`: 表示牌配列 → ドラ枚数（赤は `isRedFive` で別カウント） |

### `evaluateWin` のシグネチャ

```ts
export interface WinInput {
  concealed: TileId[];        // 和了牌を含む門前部分（14 − 3 × melds.length 枚）
  melds: MeldCall[];
  winTile: TileId;
  tsumo: boolean;
}

export interface WinSituation {
  riichi?: boolean;
  doubleRiichi?: boolean;     // 立直と置換して 2 翻
  ippatsu?: boolean;
  rinshan?: boolean;          // 嶺上開花
  haitei?: boolean;           // 海底摸月（tsumo 時のみ有効）
  houtei?: boolean;           // 河底撈魚（ロン時のみ有効）
  chankan?: boolean;          // 搶槓
  tenhou?: boolean;
  chiihou?: boolean;
  seatWind: 1 | 2 | 3 | 4;
  roundWind: 1 | 2;           // 本ゲームでは常に 1（東）
  doraIndicators: TileId[];   // 表 + 槓ドラの表示牌
  uraIndicators?: TileId[];   // 立直時のみ
}

/** 副露を含む和了手の役・符を評価する。戻り値は既存 HandValue を流用 */
export function evaluateWin(input: WinInput, sit: WinSituation): HandValue;
```

点数化は既存 `calcScore(han, fu, { dealer, tsumo, yakuman })` をそのまま使う。

### 役判定の拡張ポイント

- **食い下がり**（副露時に翻数減）: 混一色 3→2、清一色 6→5、混全帯幺九 2→1、純全帯幺九 3→2、三色同順 2→1、一気通貫 2→1
- **門前限定役の副露時除外**: 立直・一発・門前清自摸和・平和・一盃口・二盃口・七対子・国士無双・九蓮宝燈（四暗刻は暗刻数カウントで自然に除外される）。**暗槓のみの手は門前扱い**（立直可・門前清自摸和成立）
- **状況役の追加**: 嶺上開花 1・海底摸月 1・河底撈魚 1・搶槓 1・ダブルリーチ 2（立直と置換）・天和/地和（役満）・四槓子（役満）
- **暗刻カウント**: 暗槓は暗刻、明槓・加槓・ポンは明刻として三暗刻/四暗刻を判定。ロン和了で完成した刻子は明刻扱い（既存ロジック踏襲）
- **対々和・チャンタ系・三色・一通など面子構成役**: 副露面子も含めた 4 面子 + 雀頭で判定する

### 符計算の拡張ポイント

| 要素 | 中張 | 幺九 |
|---|---|---|
| 明刻（ポン・ロン完成刻子） | 2 | 4 |
| 暗刻 | 4 | 8 |
| 明槓（大明槓・加槓） | 8 | 16 |
| 暗槓 | 16 | 32 |

- 門前ロンの加符 10 符は**副露手にはつかない**
- 副露手の平和形ロン（20 符）は **30 符に切り上げ**（喰い平和形）
- 七対子 25 符・平和ツモ 20 符は門前専用のため既存ロジックのまま
- **ドラ計上は `evaluateWin` 内で行う**: `countDora(全使用牌, doraIndicators)` + 立直時 `uraIndicators` + 赤ドラ。既存の「役ゼロならドラも無効」ルールを踏襲。既存 `WinContext.doraCount`（呼び出し側で計算して渡す方式）とは異なる点に注意

## 5. 局進行状態機械

### 設計方針

進行エンジンは **React 非依存の純粋関数群**として `src/games/four-player-mahjong/engine.ts` に実装する（04 のレイヤールール上は games 層。core に置かない理由: 局進行はこのゲーム固有で、他ゲームからの再利用予定がないため。汎用化の需要が出たら core へ昇格）。

CPU の判断は決定論的なので、エンジンは「次に**人間の入力**が必要になる地点」まで自動進行できるが、UI 演出（CPU の打牌を 1 手ずつ見せる）のため **1 アクション = 1 ステップ**の粒度で `CPU_STEP` イベント駆動とする。

### フェーズ定義

```ts
export type Phase =
  | { t: "playerTurn";                 // 自家の手番（ツモ後 or 鳴き後）
      drawn: TileId | null;            // null = 鳴き直後（打牌のみ可）
      canTsumo: boolean;
      canRiichi: boolean;
      ankanKinds: number[];            // 暗槓できる牌種
      kakanKinds: number[] }           // 加槓できる牌種
  | { t: "playerClaim";                // 他家の打牌に対する自家の応答待ち
      discarded: TileId; from: Seat;
      options: ClaimOption[] }         // 常に「スルー」も選べる
  | { t: "cpuTurn"; seat: Seat }       // CPU の手番（演出タイマー待ち）
  | { t: "finished"; result: RoundResult };

export type ClaimOption =
  | { kind: "ron" }
  | { kind: "pon" }
  | { kind: "minkan" }
  | { kind: "chi"; tiles: [TileId, TileId] };  // チーの構成が複数ある場合は列挙
```

### イベント（reducer への入力）

| イベント | 発火元 | 内容 |
|---|---|---|
| `DEAL(seed)` | 開始ボタン | `mulberry32(seed)` で山生成・配牌・起家決定 |
| `DISCARD(index, riichi?)` | プレイヤー | 打牌（`index = hand.length` はツモ切り）。`riichi` 指定で立直宣言打牌 |
| `TSUMO_AGARI` | プレイヤー | ツモ和了 |
| `ANKAN(kind)` / `KAKAN(kind)` | プレイヤー | 暗槓 / 加槓 |
| `CLAIM(option)` | プレイヤー | `playerClaim` でロン/ポン/カン/チーを選択 |
| `PASS` | プレイヤー | `playerClaim` でスルー |
| `CPU_STEP` | UI のタイマー | CPU の 1 アクション（ツモ→判断→打牌 等）を進める |

### 進行ルール

1. **1 手番の流れ**: ツモ →（暗槓/加槓ループ: 加槓は搶槓チェック → 成立なら嶺上ツモ + 槓ドラ即めくり）→ 打牌 / ツモ和了 / 立直宣言打牌
2. **打牌後の裁定**: 全他家の応答（CPU は即時判断、自家に選択肢があれば `playerClaim` で停止）を収集し、**ロン ＞ ポン・カン ＞ チー**の優先順位で 1 件だけ採用。ロン競合は頭ハネ（放銃者からツモ順で最も近い 1 人）
3. **王牌**: 常に 14 枚を維持。嶺上ツモのたびに生牌山の末尾から 1 枚を王牌へ補充（＝カン 1 回でツモ可能回数が 1 減る）
4. **フリテン更新タイミング**: ①打牌時に自河フリテンを再計算 ②ロン可能牌を見逃した時に同巡フラグを立て、自分のツモ番で解除 ③立直後の見逃しは永続フラグ
5. **立直処理**: 宣言打牌がロンされなければ成立。供託 1000 移動・宣言牌を横向き表示・以後自動ツモ切り（ツモ和了と暗槓可否のみ確認）
6. **終局と精算**:
   - 和了: `evaluateWin` → `calcScore`。ロンは放銃者が全額、ツモは親 2 倍/子 1 倍（`payments` 文字列を流用）。供託 + 立直棒は和了者へ
   - 荒牌流局: 全員のテンパイ判定（`shantenWithMelds` = 0、形式テンパイ可）→ ノーテン罰符精算 → 立直棒は宣言者へ返却
   - 結果は `RoundResult`（和了者・役一覧・符翻・点数移動・裏ドラ等）に格納

### 不変条件（テストで常時検証）

- 牌の総数 = 136（山 + 王牌 + 全手牌 + 全副露 + 全河 + ツモ中の牌）
- 点数総和 = 100000 + 供託 × 0（供託は `kyotaku` に計上するため総和は常に 100000）
- 王牌は常に 14 枚

## 6. CPU AI 設計（標準 AI）

判断はすべて決定論的（乱数を使わない）。シード固定でリプレイ可能。

### 攻守判定

- **ベタオリ条件**: 立直者がいる、または「副露 3 組以上 + ドラポン」の他家がいる状況で、自分が 2 シャンテン以上
- ベタオリ時は `safetyLevel(tile, riverCounts, handCounts)` が最小の牌を切る。**見える牌すべて**（全員の河 + 全副露 + ドラ表示牌 + 自手牌）を計上して安全度を評価する
- `safetyLevel` は `src/games/betaori/logic.ts` から **`src/games/shared/safety.ts` へ昇格**して共用する（04 の「共通化したいものが出たら昇格」ルールに従う。betaori 側も昇格先を import に変更）

### 通常打牌

- `shantenWithMelds` ベースの受け入れ評価（`discardOptions` の副露対応版ヘルパーを engine 内に用意）で受け入れ最大の打牌を選ぶ
- タイブレーク: 字牌 → 端牌 → 中張牌の順に切る。赤・ドラは保持を優先

### 鳴き判断

1. **役牌ポン**: 常時実行（役が確定するため）
2. **タンヤオ・染め手**が見込め、かつ鳴くとシャンテン数が進む場合のみチー/ポン
3. 鳴いた結果**役なし濃厚**になる鳴きは禁止（現在の手牌から到達可能な役があるかの見込み判定関数を用意）
4. ドラを 3 枚以上保有しているときは鳴き基準を緩和（打点が確保されているため）
5. 大明槓は打点が向上する場合のみ。暗槓は立直者不在時は原則実行、立直者がいる場合は待ち牌の安全が読めないため見送り

### 立直判断

- テンパイ・門前なら原則即立直。待ちの残り枚数が 0 のときのみダマ（待ち替えせずツモ切り続行）

### 将来拡張

難易度分岐は「打牌選択」「鳴き判断」「ベタオリ条件」の 3 関数を差し替える形で追加する（第 1 版はフックを設けるのみ）。

## 7. UI 設計

### レイアウト（モバイル縦画面基準）

```
┌─────────────────────────┐
│ 対面(2): 手牌枚数(牌裏) + 副露        │
│          河(6 列折返し)              │
│ ┌─────────────────┐ │
│ │ 左:上家(3)の河│中央パネル│右:下家(1)の河│ │
│ │ (小サイズ縦) │ドラ表示牌 │ (小サイズ縦) │ │
│ │  + 副露     │残りツモ数 │  + 副露     │ │
│ │             │4人の点数/風│            │ │
│ └─────────────────┘ │
│ 自家(0): 河(6 列折返し)              │
│          副露                        │
│ [アクションバー(出現式)]              │
│ 手牌 13 枚 + ツモ牌(右に分離)         │
└─────────────────────────┘
```

- 他家の手牌は `Tile` の `faceDown` で牌裏表示（枚数はカンで 13 枚から減る）
- 左右家の河・副露は `small` サイズの `Tile` で省スペース表示
- 自家の手牌は既存 `Hand`（`drawn` プロパティでツモ牌を右端分離）を流用
- 中央パネル: ドラ表示牌（槓ドラはめくれた分だけ追加表示）・残りツモ数・4 人の点数と自風・供託棒

### アクション UI

- 手牌の直上に**出現式のアクションバー**: ロン / ツモ / リーチ / ポン / チー / カン / スルー
- 和了ボタン（ロン・ツモ）は色を変えて誤操作を防ぐ
- チーの構成が複数ある場合・カン対象が複数ある場合は、候補の牌ペアを牌画像つきボタンで並べて選択させる
- 立直宣言は「リーチ」タップ → 宣言可能な打牌のみ選択可能になる 2 段階操作

### 演出

- 立直宣言牌は CSS transform で横向き表示。供託棒アイコンを中央パネルに表示
- 鳴き発声（「ポン」等）はテキストの吹き出しで 800ms 表示
- CPU の打牌間隔は 300〜600ms。**高速化トグル**（設定でアニメ短縮）を用意
- **結果モーダル**: 和了手の開示 → 立直時は裏ドラめくり演出 → 役一覧（翻数付き）→ 符/翻/点数（`ScoreResult.payments` を流用）→ 4 人の点数増減。流局時は全員のテンパイ/ノーテンと手牌開示

### 戦績

- `localStorage` に `four-player-mahjong:stats` として通算成績（対局数・和了数・放銃数・最高打点）を保存（既存ゲームの命名規約 `<game>:<key>` に従う）

## 8. 状態管理と乱数

- **`useReducer` を採用**する。既存ゲームは `useState` のみだが、本ゲームは「1 つの状態（`RoundState`）に対する 8 種のイベント遷移」であり、複数 `useState` に分割すると更新の原子性が壊れるため。reducer 本体はエンジンの純粋関数 `step(state, event): RoundState` で、コンポーネントは phase を見た描画と `CPU_STEP` の setTimeout dispatch のみを担当する
- **決定論性**: `mulberry32(seed)` で `DEAL` 時に山を一括確定する。以後の進行に乱数は不要（CPU も決定論的）なので **reducer は完全に純粋**。シード指定でリプレイ・バグ再現・シナリオテストが可能
